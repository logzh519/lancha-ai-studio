PLATFORM AUTHORIZATION REVIEW

认证、账户与 RBAC 设计分析

从当前代码和迁移出发，说明外部登录如何落到内部账户，RBAC 如何授权，以及未来更换账号系统时哪些部分能复用、哪些仍需改造。

结论先行

这套设计将“认证”和“授权”分开：认证负责确认外部用户是谁，再映射到内部 user.id；授权只围绕这个内部 ID 计算角色和权限。业务模块不依赖飞书账号，也不直接消费外部 token。

账户与 RBAC 解耦只要新认证源能给出稳定身份并映射到既有 user.id，角色、权限、模块 API 无需改变。
内部会话可复用当前 cookie session、哈希存储、撤销与 Principal 形状基本是 provider-neutral 的。
当前不是即插即用Feishu 的路由、配置、启动校验和登录页都写死；“只替换 platforms/auth/feishu/”与现状不符。
切换成本判断：若新系统是相似的浏览器 OAuth/OIDC 登录，预计是小到中等范围的认证接入改造，RBAC 可保持不动；若是反向代理头、JWT 网关、LDAP 或完全不同的账号生命周期，需新增对应认证入口与身份映射策略，不能视为换一个客户端文件。

表结构与职责

下表对应当前 ORM 模型和 platform schema 的 Alembic 迁移。所有账户、认证状态与 RBAC 数据均在 PostgreSQL 的 platform schema。

表关键字段 / 约束职责与关系
userid 主键；username 唯一；display_name；is_superuser；is_active；创建/更新时间平台内部账户主表。没有密码或外部 access token；所有授权和会话最终关联它的 ID。
user_identityuser_id 外键；provider；external_id；union_id、email、avatar_url、last_login_at；唯一约束 (provider, external_id)外部身份到内部账户的映射。一个内部用户可以有关联的多个 provider 身份；删除用户时身份级联删除。没有 email 唯一约束。
user_sessiontoken_hash 主键；user_id 外键；expires_at；created_at内部会话。数据库只存原始随机 token 的 SHA-256；cookie 持有原 token。用户停用时会删除其会话。
oauth_statestate_hash 主键；nonce_hash；expires_at；created_at登录回调的一次性 state 与浏览器 nonce 绑定，防止重放和 login CSRF；消费时用原子 DELETE RETURNING。
roleid 主键；code 唯一；name；description；创建/更新时间可分配给用户的一组授权集合。
permissionid 主键；code 唯一；name；module 索引权限点注册表。代码声明是来源，数据库负责查询与角色关联。
user_roleuser_id、role_id 外键；唯一约束 (user_id, role_id)用户与角色的多对多关联；删除用户或角色时关联级联清理。
role_permissionrole_id、permission_id 外键；唯一约束 (role_id, permission_id)角色与权限点的多对多关联；删除角色或权限点时关联级联清理。
权限继承规则：一个用户拥有多个角色时，权限是这些角色权限的并集；代码没有 deny/显式拒绝优先级。超级用户由 user.is_superuser 表示，可跳过常规权限点校验。

请求如何鉴权

生产登录：飞书

  1. 登录页调用 GET /api/auth/config，检查飞书是否已配置；点击登录后调用 POST /api/auth/feishu/login-url。
  2. 后端生成随机 state/nonce，只将哈希写入 oauth_state，nonce 原文写入 HttpOnly cookie；浏览器跳转到飞书授权页。
  3. 回调校验并消费 state/nonce，使用授权码换 token、获取用户资料，整理为 ExternalProfile。
  4. identity.upsert() 按外部身份查找；未命中时尝试按规范化邮箱匹配既有 user.username，否则创建内部账户；新账户不自动授予角色。
  5. session.issue() 创建本地会话，数据库存 token 哈希，浏览器收到 HttpOnly lancha_session cookie。
  6. 后续每个请求解析会话为 Principal；无有效会话或用户被停用时视为匿名。

接口授权

业务路由声明例如 Depends(require("example:item:view"))。require() 校验用户仍有效，再查询角色关联权限；缺权限返回 403。匿名请求的权限集合为空。平台 GET /api/modules 同样按权限过滤菜单，并返回当前用户权限码。

前端可用 v-permission="'example:item:create'" 隐藏按钮或表单，但它只改善界面体验；请求是否允许必须由后端依赖再次校验。

开发登录

AUTH_MODE=dev_header 时从 X-User-Id 读取内部用户 ID，不走飞书、cookie session 或登录回调。它仅用于本地开发和测试，不应部署到生产；前端的 VITE_DEV_USER_ID 会自动附加该请求头。

怎么使用和维护

初始化

  1. 执行平台迁移：alembic -n platform upgrade head；业务模块分别执行自己的迁移。
  2. 执行 python scripts/sync_permissions.py，使模块与平台声明的权限点进入数据库。
  3. 本地开发可用 dev_header 测试；生产设置 AUTH_MODE=feishu，配置应用 ID、密钥、回调 URL，且必须设置 HTTPS 环境下的 cookie 安全选项。

首个超级管理员

首次上线需先通过 SQL 创建一个内部管理员用户（或先完成一次外部登录，再把该用户提升为超级用户）。当前 README 提供的空表开发初始化示例：

INSERT INTO platform."user" (username, display_name, is_superuser, is_active)
VALUES ('admin', 'admin', true, true);

飞书模式首次登录后，也可按邮箱查到用户再提升：

UPDATE platform."user"
SET is_superuser = true
WHERE username = '你的企业邮箱（小写）';
避免在共享环境长期使用开发态固定 ID；也不要在生产直接信任客户端传来的 X-User-Id。超级用户不受常规 RBAC 权限点约束，SQL 提权应纳入运维审计。

授权操作

  • 模块开发者在模块 module.py 声明权限码和菜单，权限码遵循 模块:资源:动作，例如 example:item:view。
  • 管理员在角色管理中创建角色并勾选权限点，再在用户管理中为用户分配角色；新登录用户默认没有任何角色。
  • 禁用用户会删除其现有 session，因此立即阻断会话；重新启用后需重新登录。
  • 权限声明变更后重跑同步脚本。删除声明会级联移除角色上的该权限绑定，发布前要确认影响面。

未来更换账号系统：能复用什么

能力 / 部分当前可复用程度判断
内部账户、角色、权限及关联表可直接复用前提是继续把外部身份映射到原有 user.id。业务模块的权限声明、服务端 require() 和 RBAC 查询无需知道 provider。
ExternalProfile 与 identity.upsert()大体复用新登录系统须能映射稳定的 provider 标识、external ID 和资料字段。邮箱自动关联策略需重新确认是否安全。
session.py 本地会话与 cookie多数场景复用新认证成功后调用 issue() 即可继续沿用本地会话；若改为每请求验证外部 JWT 或代理身份头，则可选择不使用此会话层。
Principal / current_principal需接入适配器Principal 已经是稳定边界，但当前 provider 选择和依赖覆盖是 app 初始化时按飞书模式分支；新认证源需要新的请求解析实现。
后端登录路由和设置需要修改api.py 定义飞书专属 URL；config.py 的 Literal 只有 dev_header/feishu；gateway/app.py 对飞书环境变量做启动校验。
前端登录页与 session store需要修改按钮、文案、配置响应和启动函数均直接命名 Feishu；换 provider 时需要同步改前端。
数据库迁移通常无需改表user_identity 已含 provider 与 external_id。若保留内部用户 ID 并能完成身份映射，通常无需 RBAC 迁移；但账号关联/历史身份数据可能需要一次性迁移或人工核对。

推荐切换步骤

  1. 先确认新系统的接入形态：OIDC/OAuth 回调、网关透传 JWT，还是 LDAP/其他协议；确认稳定 subject、邮箱是否验证、停用状态如何同步。
  2. 新增 provider 客户端或请求验证器，把验证结果归一为内部身份资料；认证成功后继续调用身份映射与现有 session，或者明确采用外部 token 直接解析 Principal。
  3. 替换/扩展 AUTH_MODE 配置、启动时配置验证和路由挂载；保留开发模式但禁止其成为生产回退路径。
  4. 调整登录页与前端 session store，使页面根据启用的登录方式展示入口，而不是将 provider 写死在组件与函数名中。
  5. 设计旧用户绑定策略：优先使用新系统的稳定 subject 显式绑定；邮箱只能在可信、已验证且组织策略允许时用于首次关联。必要时让用户先通过旧身份登录后绑定新身份。
  6. 上线前测试同一内部用户的角色/权限保持不变、停用用户无法重新建立会话、登出/过期行为正确，以及不同 provider 身份不会错误合并。
保持低改动的关键：继续把 RBAC 依赖在 user.id 上；身份切换只改变“如何验证外部凭证、如何得到身份资料、如何建立 Principal/会话”，不让外部 provider ID 进入业务权限表或模块代码。

当前边界与改进建议

  1. “只替换飞书目录”并不符合当前实现。认证端点在 auth/api.py，模式校验在 config.py 和 gateway/app.py，登录入口在前端 store 和 LoginView；Feishu client 只是外部 API 客户端。架构规范第 4 节应修正文案，避免未来按错误预期估算工作。
  2. 邮箱匹配等同账号自动合并。identity.upsert() 会按 email 找到已有 user.username 并绑定身份。新 provider 必须确认邮箱来自可信来源且已验证，否则可能发生账号接管；建议明确 verified email 字段或采用用户主动绑定流程。
  3. 多身份已允许，但读取侧按单身份处理。数据库仅约束 provider+external_id 唯一，允许一个用户关联多个身份；/api/auth/me 和用户列表却直接 outer join identity，未按 provider 聚合，用户多身份时可能返回重复用户行或不确定的头像/邮箱/最后登录时间。切换前应决定“一用户一个主展示身份”还是聚合资料，并修正查询。
  4. 本地账户 username 仍承担登录映射键。username 全局唯一，首次登录用规范化邮箱，缺少邮箱时退化为 provider_external_id。邮箱变更不会同步修改 username。新增身份源时需准备好缺邮箱、邮箱冲突和邮箱变更的处理规则。
  5. 认证开关的默认值是开发模式。AUTH_MODE 默认 dev_header，部署必须显式设成生产认证方式，并在部署配置/启动检查中防止漏配。不能把未知配置或 provider 故障静默回退为信任请求头。
  6. Provider 抽象应按真实第二种接入提取。当前不需要为尚未出现的 LDAP、OIDC、网关认证预设一个过度通用接口。出现第二个真实 provider 时，把 app 配置、认证路由/Principal provider、前端登录入口抽成可选择实现；OAuth 回调只是其中一种能力，不要强迫网关 JWT 也模拟 OAuth。
整体评估：授权模型边界清晰，换认证系统时 RBAC 不需要推翻；切换点尚未完全模块化，因此目前属于“数据模型已预留、应用接入未插件化”。只要在账号合并与前端/启动配置处补齐适配，切换工作可局限在平台 auth 与登录界面，不应扩散到业务模块。
