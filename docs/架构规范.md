# 架构规范

模块化单体 + Monorepo：后端按模块装载，API 进程与各模块的 worker 进程共用同一套装载流程，一个前端工程按模块划分目录。
公共能力只做一份，模块之间靠契约隔离，以后任何模块都能低成本拆出去独立部署。

## 1. 目录结构

```
lancha-ai-studio/
├─ server/
│  ├─ platforms/            平台公共能力，不得反向依赖 modules
│  │  ├─ auth/              RBAC：角色、权限点、接口级校验
│  │  ├─ gateway/           模块装载、路由挂载、请求拦截、统一错误响应
│  │  ├─ migrations/        平台表的迁移分支
│  │  ├─ config.py          平台配置
│  │  ├─ contract.py        模块对平台的契约 ModuleSpec
│  │  ├─ db.py              数据库接入与 schema 约定
│  │  ├─ events.py          进程内事件总线
│  │  ├─ lifecycle.py       模块生命周期：事件订阅、启动与关闭钩子（API 与 worker 共用）
│  │  ├─ llm/               统一 LLM 客户端（OpenAI / Anthropic 协议）
│  │  ├─ registry.py        已加载模块的注册表
│  │  ├─ storage/           对象存储（火山引擎 TOS / 华为云 OBS）
│  │  └─ worker/            worker 进程骨架：循环托管、看门狗、单例锁
│  ├─ modules/              业务模块，互不依赖
│  │  └─ example_a/         新建模块时复制这个目录
│  ├─ tests/                platforms/ 与 modules/<模块名>/ 分开放
│  ├─ migrations/           所有迁移分支共用的 env.py
│  └─ scripts/              运维脚本
├─ web/
│  └─ src/
│     ├─ shell/             布局、路由、模块装载
│     ├─ shared/            ui（主题与通用组件）、core（请求、权限、模块契约）
│     └─ modules/           业务模块，互不依赖
├─ deploy/                  Dockerfile、compose、nginx
└─ docs/
```

## 2. 命名约定

模块名一经确定，后端包名、前端目录、接口前缀、schema、权限码全部由它推导，不允许出现第二种写法。

| 项 | 规则 | 示例 |
|---|---|---|
| 模块名 | 小写字母、数字、下划线，字母开头 | `example` |
| 后端包 | `modules.<模块名>` | `modules.example` |
| 前端目录 | `src/modules/<模块名>` | `src/modules/example` |
| 接口前缀 | `/api/<模块名>` | `/api/example/items` |
| 前端路由 | `/<模块名>/...` | `/example/items` |
| 数据库 schema | `mod_<模块名>` | `mod_example` |
| 权限码 | `<模块名>:<资源>:<动作>` | `example:item:view` |
| 事件名 | `<模块名>.<事件>` | `example.item_created` |
| 配置前缀 | `<模块名大写>_` | `EXAMPLE_PAGE_SIZE` |
| 迁移分支 | `alembic -n <模块名>` | `alembic -n example` |
| 后台循环 | `<模块名>.<循环名>`，循环名规则同模块名 | `example_a.report_item_count` |
| worker 服务 | `worker-<模块名>` | `worker-example_a` |
| 循环日志 | `worker.<模块名>.<循环名>` | `worker.example_a.report_item_count` |

违反前四项及循环名规则的，`platforms/gateway/loader.py` 在进程启动时直接拒绝加载。

## 3. 模块边界

**三条铁律**

1. 依赖只能向下：`modules → platforms`。平台层永远不 import 业务模块。
2. 模块之间只能 import 对方的 `contract.py`，碰 `service` / `models` / `repository` 一律不允许。
3. 每个模块只能读写自己的 schema，禁止跨 schema 的 JOIN 和外键。唯一例外是可以引用 `platform.user.id`。

**跨模块通信只有两种方式**

- 要立刻拿到结果：调对方 `contract.py` 里的函数，返回冻结 DTO，不返回 ORM 对象。
- 只是通知别人：`platforms.events.publish("<模块名>.<事件>", payload)`，发布方不关心谁消费。

**后台逻辑放在 worker 进程**

模块在 `worker/` 中实现后台循环，经 `module.py` 的 `ModuleSpec.loops` 声明，由 `python main.py worker <模块名>` 托管运行。平台只负责托管：异常退避重启、优雅停机、事件循环看门狗、单例锁；任务表、租约、幂等、重试由模块自己实现。

- 除 `module.py` 与 `worker/` 自身外，模块内任何代码不得 import 自己的 `worker/`（架构测试检查）；`worker/` 在 import 时不得建连接、开线程或启动外部进程。
- `on_startup` / `on_shutdown` 会在 API 进程和每个装载该模块的 worker 进程中各执行一次，必须幂等，且不得启动后台任务。
- 事件只在进程内派发。worker 只装载目标模块及其 `depends_on`，它发布的事件其他模块收不到；执行只由本模块 schema 中的状态驱动，需要通知其他模块时写自己的状态表，由对方经 `contract.py` 查询。
- 不能重复执行的循环声明 `singleton=True`（PostgreSQL advisory lock，失锁即停，尽力而为）；其余循环在多副本下的并发安全由模块保证，如 `FOR UPDATE SKIP LOCKED`。
- CPU 密集操作放到线程池或子进程，事件循环阻塞超过 `WORKER_WATCHDOG_TIMEOUT`（默认 60 秒）进程会被看门狗终止。
- 循环内并发执行的子任务必须用 `asyncio.TaskGroup` 创建：循环被取消（停机超时、单例失锁）或异常重启时，子任务随之取消并等待结束，不会留下孤儿任务。子任务自己处理业务异常，否则一个子任务失败会连带取消整组；被取消时的清理（如释放租约）只用于加速恢复，正确性依赖模块自己的租约与 fence。
- worker 尽量少同步调用其他模块的 `contract.py`：拆分模块时这些调用要改成远程调用。

```python
async def report_item_count(ctx: LoopContext) -> None:
    while True:
        async with session_scope() as session:
            ...
        if not await ctx.sleep(30):      # 收到停机信号返回 False
            return

LOOPS = (BackgroundLoop("report_item_count", report_item_count),)
```

**这些约束是可执行的，不是口头约定**

- 后端：`server/tests/platforms/test_architecture.py` 用 AST 扫描所有 import，越界即测试失败。
- 后端架构测试还检查 ORM 元数据中的跨 schema 外键；只允许模块表引用 `platform.user.id`。原生 SQL 的跨 schema JOIN 不由该检查覆盖。
- 前端：`eslint-plugin-boundaries`，模块引用 shell 或其他模块直接报 error。
- 前端的 boundaries 依赖 import resolver，resolver 一旦失效规则会静默失效，因此同时开了 `boundaries/no-unknown` 兜底。

**模块内的 Tool 层**

把一项业务能力封装成可独立重跑、可跨管线复用的单元时，放在 `modules/<模块名>/tools/`，完整约定见
[Tool 抽象与规范设计](superpowers/specs/2026-10-05-tool-abstraction-design.md)。三条硬性约束：

- Tool 不读写编排状态（任务、节点、批次），不做限流与重试决策，不感知自己在管线中的位置。允许访问基础设施服务与业务数据源，但一律构造注入，不得自行读全局配置或新建实例。
- 输入输出各声明一个 Pydantic 模型。业务失败抛 `ToolError`，未预期异常不得吞成失败结果。
- 契约字段只在有真实来源时新增，不为尚不存在的调用方预留字段。

## 4. 权限模型

本框架做授权（RBAC）与认证（飞书扫码登录，可替换）。

- `platform.user` 只存身份标识，不存任何凭证。接入登录体系时，只需把认证结果映射到 `user.id`。
- 当前请求属于谁，由 `platforms/auth/principal.py` 决定。`AUTH_MODE=dev_header` 时从 `X-User-Id` 请求头取，**仅供开发自测**；`AUTH_MODE=feishu` 时由 `create_app()` 装上基于会话 cookie 的实现。换成公司自有账号系统时只需替换 `platforms/auth/feishu/`，`session.py` 与 `identity.py` 不动。
- 权限点和菜单只在后端 `module.py` 声明一次，前端不维护第二份清单。前端启动后调 `GET /api/modules` 获取当前用户可见的菜单与权限码。平台 API 使用 `/api/auth`、`/api/admin`、`/api/modules`；业务模块仍使用 `/api/<模块名>/...`，模块名不得占用 `auth`、`admin`、`modules` 等平台保留前缀。
- 接口级校验：`dependencies=[Depends(require("example:item:view"))]`。
- 按钮级校验：前端 `v-permission="'example:item:create'"`。
- 权限点落库靠 `python scripts/sync_permissions.py`，模块里删掉的权限点会连同角色绑定一起清理。

后续如果需要数据权限（例如某运营只能看指定店铺），在 `Principal` 上扩展数据域字段，并在 repository 层显式传入过滤条件——不要用 ORM 全局隐式过滤，那种问题极难排查。

**SQL 边界的执行方式**：当前架构测试能检查 ORM 声明的外键和 Python import 依赖，但不能可靠证明任意原生 SQL 没有跨模块 schema 查询。模块代码禁止拼接或直接书写跨模块 schema SQL，跨模块读取走 contract 或事件；对高保障隔离要求，应进一步使用不同数据库角色并按 schema 收紧 PostgreSQL `USAGE` / 表权限，或将 SQL 访问集中到可审计的 repository 层。仅有单元测试不能代替数据库权限隔离。

## 5. 数据库与迁移

全平台一个 PostgreSQL 库，按 schema 隔离。每个 schema 是一条独立的迁移分支，`alembic_version` 表也建在各自 schema 里，分支之间互不阻塞。

```bash
alembic -n platform revision --autogenerate -m "xxx"
alembic -n platform upgrade head
alembic -n example_a upgrade head
alembic -n platform check        # 校验模型与迁移是否一致，CI 必跑
```

带 schema 的表，SQLAlchemy 生成的索引名会带 schema 前缀（如 `ix_platform_permission_module`），手写迁移时要对齐，否则 `alembic check` 会一直有 diff。

**结构变更流程**：模型描述目标结构，迁移描述如何从上一版安全到达目标结构。自动生成只是草稿，迁移文件必须审阅并与模型一起提交。

1. 表归属哪个 schema，就改哪个模块的 `models.py`；平台表改 `platforms` 的模型。不在生产库手工改表，不让多个模块共同拥有一张业务表。
2. 在 `server` 目录按分支生成编号草稿。编号按分支单独递增，用 `--rev-id` 指定四位数字，先查 history 确认不重复；`down_revision` 必须指向该分支当前 head。已应用到共享环境的 revision ID 不得修改。
   ```bash
   python -m alembic -n <模块名> history
   python -m alembic -n <模块名> revision --autogenerate --rev-id 0002 -m "add item status"
   ```
3. 人工审阅 `upgrade()` / `downgrade()`：对象与 schema 是否正确，重命名是否被误生成成删表/建表，非空字段如何填充旧行，唯一约束是否撞现有数据，索引和外键是否符合模块边界。数据回填、字段拆分/合并、复杂约束和破坏性变更需要手写或修正迁移。
4. 在隔离数据库验证：从空库完整升级，并在可行时从上一发布版本的结构和数据升级，再跑模块测试和架构测试。测试夹具用 ORM `create_all`，不执行迁移文件，不能代替迁移验证。
   ```bash
   python -m alembic -n <模块名> upgrade head
   python -m alembic -n <模块名> check
   python -m pytest tests/modules/<模块名> tests/platforms/test_architecture.py
   ```
5. 部署时由 compose 的 `migrate` 服务运行 `scripts/migrate.py`，在后端启动前升级 platform 和已启用模块的分支并同步权限；迁移失败后端不启动。
6. 不兼容改动按“扩展 → 迁移数据 → 收缩”分版本发布：滚动发布期间新旧代码会同时访问数据库，不要在单次发布里删除旧代码仍在使用的列。

**生产安全**：上线前备份数据库并确认恢复方案。`downgrade` 不是常规回滚手段，可能丢数据或无法逆转，优先准备向前修复迁移。权限同步按已启用模块装载权限，部分启用模块时要确认不会误删其他模块的权限及角色授权。

## 6. 新增一个模块

```
后端
1. 复制 server/modules/example_a 为 server/modules/<模块名>
2. 改 module.py 的 name / title / permissions / menus
3. models.py 的 schema 会自动跟随模块名
4. 在 alembic.ini 里加一个同名 section，指向本模块的 migrations/versions
5. 复制 server/tests/modules/example_a 为 server/tests/modules/<模块名>
6. 有后台逻辑时在 worker/__init__.py 声明 LOOPS，module.py 传入 loops=LOOPS

前端
7. 复制 web/src/modules/example_a 为 web/src/modules/<模块名>
8. 改 index.ts 的 name 和路由

验证
9. cd server && pytest        架构测试会自动覆盖新模块
10. cd web && npm run lint && npm run typecheck
```

菜单 `path` 与前端路由必须对齐：后端声明 `/example_a/items`，前端模块里写 `path: 'items'`，shell 自动加前缀。

**合并前检查清单**

- 模块命名、API 前缀、路由、schema、权限码保持一致
- 没有跨业务模块导入内部 service、models 或 repository
- 没有跨模块 JOIN、外键或原生 SQL schema 访问
- 权限由后端声明并在接口层校验，前端只消费授权结果
- 数据库变更包含本模块迁移，`alembic check` 通过
- `cd server && pytest`、`cd web && npm run lint && npm run typecheck` 通过

## 7. 本地开发

```bash
# 依赖
cd deploy && docker compose -p lancha up -d postgres

# 后端
cd server
pip install -r requirements/dev.txt
cp .env.example .env
alembic -n platform upgrade head && alembic -n example_a upgrade head
python scripts/sync_permissions.py
python main.py
python main.py worker <模块名>        # 另开终端运行该模块的后台循环

# 前端
cd web
npm install
cp .env.example .env.local
npm run dev
```

只开发自己的模块时，后端设 `ENABLED_MODULES=<模块名>`，前端设 `VITE_ENABLED_MODULES=<模块名>`，启动更快，也不会被别人未完成的代码阻塞。

测试连的是 `<库名>_test` 库，由 `conftest.py` 强制并自动创建；连不上 PostgreSQL 时，标了 `@pytest.mark.db` 的用例自动跳过。

## 8. 部署

```bash
cd deploy
cp .env.example .env
docker compose -p lancha up -d --build
# 迁移与权限同步作为前置步骤单独执行，不放在容器启动命令里
docker compose -p lancha run --rm server sh -c "alembic -n platform upgrade head && alembic -n example_a upgrade head"
docker compose -p lancha run --rm server python scripts/sync_permissions.py
```

同一个镜像通过 `ENABLED_MODULES` 控制启用哪些模块，不需要为不同组合重新构建。

有后台循环的模块按 compose 中的模板各加一个 `worker-<模块名>` 服务，与 `server` 共用 `x-backend-env`，保证 `ENABLED_MODULES` 一致。worker 只装载目标模块，模块不在 `ENABLED_MODULES` 中时拒绝启动。轻量模块可以合并为 `python main.py worker a,b`；模块内的重循环可以用 `--loops` 拆到单独的服务。需要系统依赖（浏览器、ffmpeg 等）的模块提供自己的 `worker.Dockerfile`，不进 API 镜像。

## 9. 当前刻意不做的事

多租户、数据权限、微服务拆分、前端运行时微前端、后台任务队列、模块脚手架命令。
后台循环托管已支持（见第 3 节），但通用任务队列、cron 调度、跨进程事件仍不做，需要时由模块在自己的 schema 内实现。
这些都不是现在的瓶颈，需要时再按上面的边界约束逐项加入，不会推倒重来。
认证已接入飞书扫码登录（见第 4 节），多 provider 注册表尚未抽象——等出现第二个真实实现时再提取。
