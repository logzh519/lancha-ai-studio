架构设计思想
与模块化开发规范

一份同时面向管理决策与工程协作的说明：解释系统为什么这样组织、代码应该放在哪里、模块如何安全地一起演进。

架构形态：模块化单体工程形态：Monorepo核心约束：模块边界可验证
核心结论设计思想架构分层 工程结构模块规范开发流程演进策略
01 / BRIEF

先说结论

当前阶段以清晰边界和可验证约束，换取交付效率与未来调整空间。

架构主张

先把单体做成有边界的系统，再让真实需求决定是否拆分。

一个前后端 Monorepo、一套统一平台能力、多个彼此隔离的业务模块。部署与协作保持简单，模块通过契约隔离，避免共享数据库和代码把系统重新拧成一团。

为什么不先上微服务当前规模与团队协作尚不需要承担分布式部署、链路治理和数据一致性的额外成本。
为什么强调模块边界边界明确，才能独立理解、测试、替换；未来拆分时才有可用的切分面。
为什么公共能力归平台认证、权限、装载和基础设施只实现一次，避免每个业务模块重复造轮子。
为什么规则要自动检查约定由架构测试和 lint 规则执行，降低代码评审对个人记忆的依赖。
02 / WHY

设计思想：简单，但不松散

架构不是技术名词的集合，而是团队对变化成本、故障范围和协作方式作出的共同选择。

01 · DELIVERY

以当前问题为中心

先解决真实瓶颈，不为尚未出现的规模预建复杂系统。简单方案也要保留清楚的升级路径。

02 · BOUNDARY

高内聚，低耦合

一个业务能力的接口、数据和实现尽量收在同一模块内；跨模块只交换稳定契约，不共享内部细节。

03 · OWNERSHIP

数据归属明确

模块拥有自己的表与迁移分支。跨模块关系通过标识和契约表达，不依赖跨 schema JOIN 或外键。

04 · REUSE

平台只承载共性

平台提供身份、授权、模块装载、数据库接入等横向能力，不吸收某个业务的专有流程和数据模型。

05 · PROOF

架构约束可验证

后端 import 边界由 AST 测试检查，前端边界由 ESLint 检查，模型与迁移一致性纳入 CI。

06 · EVOLVE

按信号逐步演进

先记录拆分触发条件。性能、故障域或独立交付真的成为问题时，再调整进程和部署边界。

03 / MODEL

系统架构：从用户界面到数据与外部服务

业务模块是系统变化的主要承载单元；平台能力支撑模块运行，但不反向依赖业务。

职责分界：平台负责“怎样装载和治理模块”；业务模块负责“业务如何工作”。平台不 import 业务实现，业务不越界读取其他模块的内部表。

平台框架已具备的基础

模块化单体与 Monorepo、平台 / 业务目录分层、FastAPI 网关和模块注册、RBAC、schema 与迁移约定、后端架构边界测试及前端边界 lint。

业务异步执行的设计方向

长耗时工作由业务模块持有状态机、重试与执行策略。V5 设计提出模块声明后台循环，由 worker 启动；该执行方案应以对应业务实现与评审结论为准，不等同于 Celery 已是框架能力。

平台 API 命名：认证为 /api/auth/...，管理接口为 /api/admin/...，模块与权限清单为 /api/modules；业务模块继续使用 /api/<模块名>/...。auth、admin、modules 为保留模块名。

04 / REPO

工程结构：按职责分层，按业务组织

后端与前端各自保留平台 / 业务边界；同一业务的实现尽量聚合在自己的模块目录。

lancha-ai-studio/ ├─ server/ │ ├─ platforms/ 平台公共能力，不依赖业务 modules │ │ ├─ auth/ 身份、会话、RBAC 与权限校验 │ │ ├─ gateway/ 应用创建、模块装载、路由与中间件 │ │ ├─ contract.py 平台与业务模块之间的模块契约 │ │ ├─ db.py 数据库接入与 schema 约定 │ │ ├─ events.py 进程内事件发布与订阅 │ │ └─ registry.py 已加载模块注册表 │ ├─ modules/ │ │ ├─ example/ 可复制的业务模块样板 │ │ │ ├─ api.py HTTP 接口 │ │ │ ├─ service.py 用例与业务逻辑 │ │ │ ├─ models.py 本模块 ORM 模型 │ │ │ ├─ contract.py 对外 DTO 与稳定能力 │ │ │ ├─ module.py 名称、路由、菜单与权限声明 │ │ │ └─ migrations/ 本模块迁移版本 │ ├─ tests/platforms/ 平台与架构约束测试 │ ├─ tests/modules/<name>/ 业务模块测试 │ ├─ migrations/ Alembic 共用环境入口 │ └─ scripts/ 权限同步等运维脚本 ├─ web/src/ │ ├─ shell/ 应用壳、布局、路由与模块装载 │ ├─ shared/core/ 请求、会话、权限、模块契约 │ ├─ shared/ui/ 主题与可复用 UI 能力 │ └─ modules/<name>/ 页面、业务组件、API 与模块路由 ├─ deploy/ Docker、Compose、Nginx 配置 └─ docs/ 架构规范、设计决策与使用说明

platforms 是基础设施层

只放多个业务模块共同需要的机制。业务专有的表、流程和规则不进入平台。

modules 是业务所有权边界

模块拥有自己的 API、服务、模型、迁移、权限声明和测试；模块可以单独启停。

shell 与 shared 不等于业务层

shell 管应用组合；shared 放稳定、通用的前端能力，不成为跨模块共享业务逻辑的后门。

05 / RULES

模块化开发规范：把边界落到日常代码

以下约定用于新增功能、代码评审和自动化检查，是模块可组合运行的基础条件。

R1
依赖方向只能向下

modules → platforms。平台层永远不导入业务模块；业务模块不得反向依赖平台实现细节之外的上层组合代码。

R2
模块之间只依赖契约

需要即时结果时调用对方 contract.py 暴露的函数，返回冻结 DTO；禁止 import 对方的 service、models 或 Repository。

R3
数据按 schema 隔离

每个模块只读写自己的 schema；禁止跨模块 JOIN 与外键。跨模块业务读取走契约，弱一致性通知走事件。允许模块表引用 platform.app_user.id。

R4
命名保持端到端一致

模块名统一推导后端包、前端目录、API 前缀、路由、schema、权限码、配置前缀和迁移分支，不引入别名。

R5
权限声明以后端为准

权限点与菜单在模块声明一次，前端从平台接口取得当前用户可见信息；接口用依赖校验，按钮按权限码控制。

R6
跨模块事件只表达事实

发布方描述已发生的业务事实，不关心消费者。事件 payload 使用稳定数据结构，不传 ORM 实例，不借事件隐式调用同步业务。

R7
迁移跟随数据所有者

平台表与各模块表使用独立 Alembic 分支。模型变更必须提交迁移，并运行对应分支升级与 alembic check。

R8
跨域 SQL 不绕过边界

架构测试可检查 Python import 与 ORM 外键，但无法证明任意原生 SQL 安全。模块禁止编写跨模块 schema SQL；高保障隔离需再配数据库角色权限。

跨模块沟通的选择

同步，需要结果

调用对方公开契约

适用于当前用例必须立即拿到对方结果的场景。契约定义输入、输出和失败语义；调用方不关心服务内部如何实现。

result = await catalog.contract.get_product(product_id)
# result 是稳定 DTO，不是 ORM Model
异步，只需通知

发布领域事件

适用于“某事实已经发生，其他模块可自行响应”的场景。发布方不持有消费者列表，也不等待消费者执行。

events.publish(
    "catalog.product_imported",
    {"product_id": product_id},
)
06 / BUILD

新增模块与交付检查

沿用样板目录和统一验证命令，让新模块从第一天就符合装载、权限、数据和前端边界约定。

复制样板

从 server/modules/example 和 web/src/modules/example 建立同名模块目录。

声明模块身份

更新 module 名称、路由、菜单、权限码、schema、配置前缀与迁移分支。

实现模块闭环

将 API、用例逻辑、模型、前端页面和测试放在本模块边界内；跨模块使用契约或事件。

验证后集成

跑后端测试、前端 lint/typecheck、迁移一致性检查，再验证模块启停与权限表现。

只开发一个模块：按需装载与安装依赖

后端：只启用自己的模块

把模块名写入 server/.env，平台依赖与模块依赖分开安装。

# server/.env
ENABLED_MODULES=example

cd server
pip install -r requirements/dev.txt
pip install -r modules/example/requirements.txt

平台与开发工具从 requirements/dev.txt 安装；只额外安装自己模块的 requirements.txt，其他模块不会被网关装载。

前端：只装配自己的模块

把模块名写入 web/.env.local，开发服务器仅动态导入启用模块入口。

# web/.env.local
VITE_ENABLED_MODULES=example

cd web
npm install
npm run dev

模块入口按需加载并独立拆分；日常开发只执行自己的模块代码，不把所有模块静态并入应用入口。

依赖边界：后端支持模块级 Python 依赖文件。当前前端仍使用 Monorepo 根级 web/package.json 管理共享 npm 依赖，VITE_ENABLED_MODULES 控制模块装配与动态加载，不代表每个模块拥有独立 npm 安装环境；生产构建会为模块入口生成独立 chunk。

合并前检查清单

模块命名、API 前缀、路由、schema、权限码保持一致
没有跨业务模块导入内部 service、models 或 repository
没有跨模块 JOIN、外键或原生 SQL schema 访问
权限由后端声明并在接口层校验，前端只消费授权结果
数据库变更包含本模块迁移，迁移检查通过
边界测试、模块测试、前端 lint 与 typecheck 通过
建议的标准验证命令：后端运行 cd server && pytest；前端运行 cd web && npm run lint && npm run typecheck；涉及模型变更时运行对应迁移分支的 alembic check。
07 / NEXT

演进策略：边界先行，部署随后

模块化不是微服务的过渡期标签，而是当前架构的组织方式。是否拆进程，取决于明确的工程信号。

现在：模块化单体

统一代码库和运行载体；模块独立命名、数据归属、测试与权限；平台复用横向能力。

→

出现信号：定位瓶颈

独立扩缩容成为必要；故障需要隔离；资源争抢影响关键流程；模块需要独立发布或独立值守。

→

按边界拆分：逐步服务化

优先把已有模块边界变成进程边界；明确 API、数据所有权、可靠消息和运维责任，再引入分布式治理。

刻意暂缓：在没有真实需求前，不引入多租户、运行时微前端、分布式任务平台或模块脚手架等额外复杂度。异步执行、数据域和调度等能力按业务需要逐项补齐，不把规划能力描述成已落地能力。
