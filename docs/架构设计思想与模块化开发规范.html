Lancha AI Studio · Engineering Architecture

架构设计
与模块化开发规范

一个代码库、一套平台能力、多个边界清晰的业务模块。API 进程与各模块的 worker 进程共用同一套模块装载流程，模块可以单独启停、单独部署后台执行。

架构形态：模块化单体工程形态：Monorepo运行形态：API 进程 + 按模块的 worker 进程核心约束：模块边界可验证

01 / BRIEF

先说结论

当前阶段以清晰边界和可验证约束，换取交付效率与未来调整空间。

架构主张

先把单体做成有边界的系统，再让真实需求决定是否拆分。

一个前后端 Monorepo、一套统一平台能力、多个彼此隔离的业务模块。部署与协作保持简单，模块通过契约隔离，避免共享数据库和代码把系统重新拧成一团。

为什么不先上微服务当前规模与团队协作尚不需要承担分布式部署、链路治理和数据一致性的额外成本。
为什么强调模块边界边界明确，才能独立理解、测试、替换；未来拆分时才有可用的切分面。
为什么公共能力归平台认证、权限、装载和基础设施只实现一次，避免每个业务模块重复造轮子。
为什么规则要自动检查约定由架构测试和 lint 规则执行，降低代码评审对个人记忆的依赖。
02 / WHY

设计思想：简单，但不松散

架构不是技术名词的集合，而是团队对变化成本、故障范围和协作方式作出的共同选择。

01 · DELIVERY

以当前问题为中心

先解决真实瓶颈，不为尚未出现的规模预建复杂系统。简单方案也要保留清楚的升级路径。

02 · BOUNDARY

高内聚，低耦合

一个业务能力的接口、数据和实现尽量收在同一模块内；跨模块只交换稳定契约，不共享内部细节。

03 · OWNERSHIP

数据归属明确

模块拥有自己的表与迁移分支。跨模块关系通过标识和契约表达，不依赖跨 schema JOIN 或外键。

04 · REUSE

平台只承载共性

平台提供身份、授权、模块装载、数据库接入等横向能力，不吸收某个业务的专有流程和数据模型。

05 · PROOF

架构约束可验证

后端 import 边界由 AST 测试检查，前端边界由 ESLint 检查，模型与迁移一致性纳入 CI。

06 · EVOLVE

按信号逐步演进

先记录拆分触发条件。性能、故障域或独立交付真的成为问题时，再调整进程和部署边界。

03 / MODEL

系统架构：从用户界面到数据与外部服务

业务模块是系统变化的主要承载单元；平台能力支撑模块运行，但不反向依赖业务。

职责分界：平台负责“怎样装载和治理模块”；业务模块负责“业务如何工作”。平台不 import 业务实现，业务不越界读取其他模块的内部表。

平台框架已具备的基础

模块化单体与 Monorepo、平台 / 业务目录分层、FastAPI 网关和模块注册、RBAC、schema 与迁移约定、后端架构边界测试及前端边界 lint；worker 骨架：模块声明后台循环，平台负责异常退避重启、优雅停机、事件循环看门狗和 PostgreSQL 单例锁。

业务异步执行由模块自己实现

平台只托管循环，不提供任务队列或调度平台（也没有 Celery）。任务表、状态机、租约、幂等与重试由业务模块在自己的 schema 中实现。tiktok_studio 等业务模块（V5 设计）后续按本文 worker 接入规范独立接入。

平台 API 命名：认证为 /api/auth/...，管理接口为 /api/admin/...，模块与权限清单为 /api/modules；业务模块继续使用 /api/<模块名>/...。auth、admin、modules 为保留模块名。

04 / REPO

工程结构：按职责分层，按业务组织

后端与前端各自保留平台 / 业务边界；同一业务的实现尽量聚合在自己的模块目录。

lancha-ai-studio/ ├─ server/ │ ├─ platforms/ 平台公共能力，不依赖业务 modules │ │ ├─ auth/ 身份、会话、RBAC 与权限校验 │ │ ├─ gateway/ 应用创建、模块装载、路由与中间件 │ │ ├─ worker/ worker 进程骨架：循环托管、看门狗、单例锁 │ │ ├─ config.py 平台配置 │ │ ├─ contract.py 平台与业务模块之间的模块契约（含 BackgroundLoop） │ │ ├─ db.py 数据库接入、schema 约定与 session_scope │ │ ├─ events.py 进程内事件发布与订阅 │ │ ├─ lifecycle.py 事件订阅、启动与关闭钩子（API 与 worker 共用） │ │ └─ registry.py 已加载模块注册表 │ ├─ modules/ │ │ ├─ example_a/ 可复制的业务模块样板 │ │ │ ├─ api.py HTTP 接口 │ │ │ ├─ service.py 用例与业务逻辑 │ │ │ ├─ models.py 本模块 ORM 模型 │ │ │ ├─ contract.py 对外 DTO 与稳定能力 │ │ │ ├─ config.py 本模块配置（环境变量前缀） │ │ │ ├─ worker/ 后台循环，只由 module.py 引用 │ │ │ ├─ module.py 名称、路由、菜单、权限与后台循环声明 │ │ │ ├─ requirements.txt 本模块额外的 Python 依赖 │ │ │ └─ migrations/ 本模块迁移版本 │ │ └─ example_b/ 订阅 example_a 事件的第二个样板 │ ├─ tests/platforms/ 平台与架构约束测试 │ ├─ tests/modules/<name>/ 业务模块测试 │ ├─ migrations/ Alembic 共用环境入口 │ ├─ scripts/ 迁移、权限同步等运维脚本 │ └─ main.py 启动入口：api（默认）/ worker <模块名> ├─ web/src/ │ ├─ shell/ 应用壳、布局、路由与模块装载 │ ├─ shared/core/ 请求、会话、权限、模块契约 │ ├─ shared/ui/ 主题与可复用 UI 能力 │ └─ modules/<name>/ 页面、业务组件、API 与模块路由 ├─ deploy/ Docker、Compose、Nginx 配置 └─ docs/ 架构规范、设计决策与使用说明

platforms 是基础设施层

只放多个业务模块共同需要的机制。业务专有的表、流程和规则不进入平台。

modules 是业务所有权边界

模块拥有自己的 API、服务、模型、迁移、权限声明、后台循环和测试；模块可以单独启停，后台执行可以单独部署。

shell 与 shared 不等于业务层

shell 管应用组合；shared 放稳定、通用的前端能力，不成为跨模块共享业务逻辑的后门。

05 / RULES

模块化开发规范：把边界落到日常代码

以下约定用于新增功能、代码评审和自动化检查，是模块可组合运行的基础条件。

R1
依赖方向只能向下

modules → platforms。平台层永远不导入业务模块；业务模块不得反向依赖平台实现细节之外的上层组合代码。

R2
模块之间只依赖契约

需要即时结果时调用对方 contract.py 暴露的函数，返回冻结 DTO；禁止 import 对方的 service、models 或 Repository。

R3
数据按 schema 隔离

每个模块只读写自己的 schema；禁止跨模块 JOIN 与外键。跨模块业务读取走契约，弱一致性通知走事件。允许模块表引用 platform.user.id。

R4
命名保持端到端一致

模块名统一推导后端包、前端目录、API 前缀、路由、schema、权限码、配置前缀和迁移分支，不引入别名。

R5
权限声明以后端为准

权限点与菜单在模块声明一次，前端从平台接口取得当前用户可见信息；接口用依赖校验，按钮按权限码控制。

R6
跨模块事件只表达事实

发布方描述已发生的业务事实，不关心消费者。事件 payload 使用稳定数据结构，不传 ORM 实例，不借事件隐式调用同步业务。

R7
迁移跟随数据所有者

平台表与各模块表使用独立 Alembic 分支。模型变更必须提交迁移，并运行对应分支升级与 alembic check。

R8
跨域 SQL 不绕过边界

架构测试可检查 Python import 与 ORM 外键，但无法证明任意原生 SQL 安全。模块禁止编写跨模块 schema SQL；高保障隔离需再配数据库角色权限。

R9
后台逻辑只进 worker

后台循环写在模块的 worker/ 中，经 ModuleSpec.loops 声明，由 python main.py worker <模块名> 运行；API 进程内不启动后台任务。除 module.py 与 worker/ 自身外，模块代码不得 import 自己的 worker/，由架构测试检查。

06 / WORKER

后台 worker：平台托管，模块实现

每个有后台逻辑的模块在自己的 worker/ 中实现循环，平台只负责把循环跑稳。默认一个模块一个 worker 进程，模块剥离时连同 worker 一起带走。

职责归属说明
装载与生命周期平台只装载目标模块及其 depends_on，与 API 共用 lifecycle.py：订阅事件、执行 on_startup / on_shutdown、关闭数据库连接。目标模块不在 ENABLED_MODULES 中时拒绝启动。
异常退避重启平台循环抛出异常后按 1、2、4…60 秒退避重启，单次运行超过 60 秒后退避重置。循环正常 return 视为结束，不再重启。
优雅停机平台收到 SIGTERM / SIGINT 后设置停机事件，ctx.sleep 立即返回 False；每个循环在自己的 stop_timeout（默认 30 秒）内退出，超时被取消。
事件循环看门狗平台事件循环阻塞超过 WORKER_WATCHDOG_TIMEOUT（默认 60 秒）时打印全部线程堆栈并退出进程，由容器重启；写日志卡住时 5 秒后强制退出。
单例循环平台singleton=True 的循环先抢 PostgreSQL advisory lock，抢不到的副本待命；持锁期间每 10 秒探活，失锁即取消循环。
任务表、状态机、租约、幂等、重试模块写在模块自己的 schema 中。平台不提供任务队列、调度或跨模块执行。
模块侧 · 声明循环

worker/__init__.py 与 module.py

循环接收 LoopContext，用 session_scope() 读写本模块数据，用 ctx.sleep 等待并响应停机。

async def report_item_count(ctx: LoopContext) -> None:
    while True:
        async with session_scope() as session:
            count = await service.count_items(session)
        ctx.logger.info("当前条目数：%d", count)
        if not await ctx.sleep(30):   # 停机时返回 False
            return

LOOPS = (BackgroundLoop("report_item_count", report_item_count),)

# module.py
MODULE = ModuleSpec(name="example_a", ..., loops=LOOPS)
运行侧 · 进程拓扑

python main.py worker

默认每个模块一个进程；轻量模块可以合并，重循环可以用 --loops 拆到单独进程（仅限单个模块）。

python main.py worker example_a                        # 一个模块一个进程
python main.py worker a,b                              # 合并多个轻量模块
python main.py worker example_a --loops report_item_count   # 只跑指定循环

BackgroundLoop(
    "dispatch", run,
    stop_timeout=30.0,   # 停机等待上限
    singleton=True,      # 多副本下只有一个在跑
)

worker 接入规范

W1
worker/ 无 import 副作用

API 进程也会经 module.py 导入 worker/，import 时不得建连接、开线程或启动外部进程；资源在循环内创建、在循环内释放。

W2
启动钩子必须幂等

on_startup / on_shutdown 在 API 进程和每个装载该模块的 worker 进程中各执行一次，不得在钩子里启动后台任务。

W3
执行由数据库状态驱动

事件只在进程内派发，worker 发布的事件其他模块收不到。需要通知其他模块时写自己的状态表，由对方经 contract.py 查询；尽量少同步调用其他模块的契约，拆分时这些调用要改成远程调用。

W4
并发安全由模块保证

不能重复执行的循环声明 singleton=True；单例锁是尽力而为（不支持 PgBouncer transaction 模式），关键写入仍需幂等。其余循环在多副本下用 FOR UPDATE SKIP LOCKED 等方式抢任务。

W5
不阻塞事件循环

CPU 密集或同步阻塞操作放到线程池或子进程；阻塞超过看门狗阈值，进程会被终止。

W6
响应停机

等待一律用 ctx.sleep，并在返回 False 时尽快退出；compose 的 stop_grace_period 要大于该模块循环最大的 stop_timeout。

W7
子任务用 TaskGroup 收拢

循环内并发执行的子任务必须用 asyncio.TaskGroup 创建：循环被取消（停机超时、单例失锁）或异常重启时，子任务随之取消并等待结束，不会留下孤儿任务继续占用配额。子任务自己处理业务异常，否则一个失败会连带取消整组；被取消时的清理（如释放租约）只用于加速恢复，正确性依赖模块自己的租约与 fence。

部署：每个模块一个 worker 服务

按 deploy/docker-compose.yml 中的注释模板添加服务，与 server、migrate 共用 x-backend-env，保证 ENABLED_MODULES 一致。

worker-<模块名>:
  build: *server-build
  command: ["python", "main.py", "worker", "<模块名>"]
  restart: unless-stopped
  stop_grace_period: 60s
  environment:
    <<: *backend-env
    POSTGRES_POOL_SIZE: 3
  depends_on:
    postgres: { condition: service_healthy }
    migrate: { condition: service_completed_successfully }

部署注意事项

以下几点决定 worker 能否稳定运行和独立剥离。

# 连接池：每个持锁的单例循环额外占用一个连接
# 系统依赖（浏览器、ffmpeg 等）放进模块自己的
#   modules/<模块名>/worker.Dockerfile，不进 API 镜像
# ENABLED_MODULES 不一致会出现「能建单但没人执行」的静默故障
# 剥离模块：带走 modules/<模块名>/、对应 schema
#   与 worker 服务，跨模块契约调用改为远程调用
07 / BUILD

新增模块与交付检查

沿用样板目录和统一验证命令，让新模块从第一天就符合装载、权限、数据和前端边界约定。

复制样板

从 server/modules/example_a、server/tests/modules/example_a 和 web/src/modules/example_a 建立同名模块目录，并在 alembic.ini 加同名 section。

声明模块身份

更新 module 名称、路由、菜单、权限码、schema、配置前缀与迁移分支。

实现模块闭环

将 API、用例逻辑、模型、前端页面和测试放在本模块边界内；有后台逻辑时在 worker/ 声明 LOOPS，module.py 传入 loops=LOOPS；跨模块使用契约或事件。

验证后集成

跑后端测试、前端 lint/typecheck、迁移一致性检查，再验证模块启停、权限表现和 worker 的启动与停机。

数据库结构变更：从模型到生产

模型描述目标结构；Alembic 迁移描述如何从上一版数据库安全到达目标结构。自动生成只提供草稿，迁移文件必须审阅并与模型一起提交。

1. 修改所属模块的 ORM 模型

表归属哪个 schema，就修改哪个模块的 models.py；平台表修改 platforms 模型。不要直接在生产数据库手工改表，也不要让多个模块共同拥有一张业务表。

2. 检查分支并生成编号草稿

在 server 目录按 schema 所属分支生成。迁移编号按分支单独递增，使用 --rev-id 指定四位数字 ID，文件名由 ID 和描述 slug 组成。

python -m alembic -n example_a history
python -m alembic -n example_a revision --autogenerate --rev-id 0003 -m "add item status"
# 示例生成：modules/example_a/migrations/versions/0003_add_item_status.py

此处假设该分支已有两个 revision；实际先查 history 并确认编号未重复，再取下一个编号。down_revision 必须指向该分支当前 head。已应用到共享环境的 revision ID 不得为了改名而修改。

3. 人工审阅并补全迁移

确认 upgrade() 与 downgrade() 的对象和 schema 正确。重点检查重命名是否被误生成成删表/建表、非空字段如何填充旧行、唯一约束是否会撞现有数据，以及索引和外键是否符合模块边界。

数据回填、字段拆分/合并、复杂约束和破坏性变更通常需要手写或修正迁移；自动生成无法推断业务语义。

4. 在隔离数据库验证新旧两条路径

分别从空库完整升级，以及从上一发布版本的结构和数据升级；再跑模块测试和架构测试。测试夹具若使用 ORM create_all，它不会执行 Alembic 文件，不能代替迁移验证。

python -m alembic -n example_a upgrade head
python -m alembic -n example_a check
python -m pytest tests/modules/example_a tests/platforms/test_architecture.py

5. 提交并让部署任务升级

提交模型与迁移文件。生产部署的 migrate 一次性服务运行 scripts/migrate.py，在后端启动前升级 platform 和已启用模块的迁移分支，并同步权限；迁移失败时后端不会启动。发布后检查迁移日志、健康检查和关键读写流程。

6. 对不兼容改动分阶段发布

优先采用“扩展、迁移数据、收缩”：先增加兼容的新列/结构并发布兼容代码，再回填与切换读写，稳定后另发版本删除旧结构。滚动发布期间新旧代码可能同时访问数据库，不要在单次发布里删除仍被旧代码使用的列。

生产安全检查：上线前做数据库备份并确认恢复方案。不要把 downgrade 当作常规回滚按钮：降级可能丢数据或无法逆转业务转换，优先准备向前修复迁移。权限同步会删除代码中已移除的权限及其角色授权；当前脚本按启用模块装载权限，部分启用模块时要确认不会把其他模块权限误删。

只开发一个模块：按需装载与安装依赖

后端：只启用自己的模块

把模块名写入 server/.env，平台依赖与模块依赖分开安装。

# server/.env
ENABLED_MODULES=example_a

cd server
pip install -r requirements/dev.txt
pip install -r modules/example_a/requirements.txt
python main.py                        # API
python main.py worker example_a       # 另开终端运行后台循环

平台与开发工具从 requirements/dev.txt 安装；只额外安装自己模块的 requirements.txt，其他模块不会被网关和 worker 装载。

前端：只装配自己的模块

把模块名写入 web/.env.local，开发服务器仅动态导入启用模块入口。

# web/.env.local
VITE_ENABLED_MODULES=example_a

cd web
npm install
npm run dev

模块入口按需加载并独立拆分；日常开发只执行自己的模块代码，不把所有模块静态并入应用入口。

依赖边界：后端支持模块级 Python 依赖文件。当前前端仍使用 Monorepo 根级 web/package.json 管理共享 npm 依赖，VITE_ENABLED_MODULES 控制模块装配与动态加载，不代表每个模块拥有独立 npm 安装环境；生产构建会为模块入口生成独立 chunk。

合并前检查清单

模块命名、API 前缀、路由、schema、权限码保持一致
没有跨业务模块导入内部 service、models 或 repository
没有跨模块 JOIN、外键或原生 SQL schema 访问
权限由后端声明并在接口层校验，前端只消费授权结果
数据库变更包含本模块迁移，迁移检查通过
边界测试、模块测试、前端 lint 与 typecheck 通过
后台循环经 ModuleSpec.loops 声明，worker/ 无 import 副作用
循环用 ctx.sleep 响应停机，不能重复执行的循环声明 singleton=True
建议的标准验证命令：后端运行 cd server && pytest；前端运行 cd web && npm run lint && npm run typecheck；涉及模型变更时运行对应迁移分支的 alembic check。

演进策略：边界先行，部署随后

模块化不是微服务的过渡期标签，而是当前架构的组织方式。是否拆进程，取决于明确的工程信号。

现在：模块化单体

统一代码库和镜像；一个 API 进程加按模块的 worker 进程；模块独立命名、数据归属、测试、权限与后台执行；平台复用横向能力。

→

出现信号：定位瓶颈

独立扩缩容成为必要；故障需要隔离；资源争抢影响关键流程；模块需要独立发布或独立值守。

→

按边界拆分：逐步服务化

优先把已有模块边界变成进程边界：模块的 worker 已是独立进程，剥离时再把 API 与跨模块契约调用改为远程调用；明确数据所有权、可靠消息和运维责任，再引入分布式治理。

刻意暂缓：在没有真实需求前，不引入多租户、运行时微前端、分布式任务平台或模块脚手架等额外复杂度。worker 骨架只负责托管循环；任务队列、定时调度、跨进程事件等能力按业务需要逐项补齐，不把规划能力描述成已落地能力。
